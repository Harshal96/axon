# GraphQL support in Axon graph builds

The SDL parser and first TypeScript/Apollo adapter are implemented. See the [supported patterns](../../v1.md#graphql) and the [plan for the next adapters](2026-11-27-next-graphql-adapters.md).

**Outcome.** After an ordinary `axon index`, a developer can open `Query.order`, see its schema declaration and resolver, follow the resolver into its outbound calls, and find indexed code that requests the field. The same result should be available from the API index job. This is a plan for indexing application source. Axon's own HTTP API remains the entry point.

**First delivery.** Start with schema definition language (SDL) and executable documents. Then add one end-to-end adapter for schema-first TypeScript with Apollo Server and Apollo Client. The current checkout (`ad60d12`) already extracts TypeScript symbols, relative imports, and outbound Axios calls. This makes it possible to verify a complete caller → field → resolver → REST dependency on one small fixture. The schema and operation parser can be reused by other languages.

## What the graph should mean

| Evidence in the repository | Graph result |
| --- | --- |
| The `orders` service publishes `type Query { order(id: ID!): Order, status: String }` | Two service-owned endpoints, `Query.order` and `Query.status`. The SDL source contributes an `ApiSpec → DEFINES → ApiEndpoint` edge at each field's line. |
| A server registers `Query: { order: loadOrder }` for that schema | The existing `loadOrder` symbol gains a `HANDLES` edge to the field. Its helper calls and HTTP dependencies become navigable through the existing traversal. |
| A function submits `query OrderPage { current: order(id: "1") { id } status }` to that service | Two `CALLS_API` edges from the calling symbol, one to `Query.order` and one to `Query.status`. `OrderPage`, the alias, the invocation, and the selections are evidence. The nested `id` adds no root endpoint. |
| The same document is checked in but has no evidenced execution site | Parse and cache the operation and its fragments. It contributes zero calls or provider endpoints. |
| A proven GraphQL execution has a computed document or an ambiguous target | Preserve the call as a GraphQL `ExternalApi` with the call site, reason and any supported candidates. A raw HTTP call to `/graphql` with an unknown body can still follow Axon's HTTP rules. |

Use a distinct endpoint ID namespace, for example `endpoint::acme::orders::graphql::default::Query.order`. Store `protocol=graphql`, `schema_id`, `operation_kind`, `root_type`, `field`, and `coordinate`. Keep the transport URL as optional binding evidence. Matching is case-sensitive. A custom root such as `schema { query: Storefront }` yields `Storefront.order` with operation kind `query`. SDL files may extend the same root. The file path and client operation name play no part in provider identity. [GraphQL root operation types](https://spec.graphql.org/September2025/#sec-Root-Operation-Types)

The proposed first release supports one logical schema (`default`) per service, across any number of evidenced SDL files, and links services in the same indexed repository. A service can identify standalone schema files through its existing `specs` list. A supported server registration can also supply schema evidence. A client-side schema copy alone does not establish a provider. If two independent server schemas are evident in one service, report the scope conflict before merging any of their fields. Named schemas per service, federation ownership and cross-repository relinking are follow-ups.

### 3. Connect registered resolvers to existing symbols

### 4. Link client executions to the fields they select

Associate the client with a provider through evidenced client configuration, such as a static `HttpLink` URI matching a declared service base URL and known mount. Resolve within that target schema only. Unknown hosts, multiple candidates, and computed documents get an unresolved reason. [Apollo Client methods](https://www.apollographql.com/docs/react/api/core/ApolloClient) · [HttpLink](https://www.apollographql.com/docs/react/api/link/apollo-link-http)

[Apollo fetch policies](https://www.apollographql.com/docs/react/data/queries#supported-fetch-policies)

## Release check

Run the infrastructure-free Python suite and eval harness, Ruff and mypy, the MCP tests, and the web typecheck/test/build commands in `AGENTS.md`. Use the installed-wheel smoke test and live Neo4j tier in `CONTRIBUTING.md` to check the packaged parser and a mixed graph publish, reload, and replacement. The end-to-end check is to open `orders / Query.order`, navigate to its resolver and REST dependency, and see the two-field caller exactly once in its inbound list. After removing `order` and reindexing, the two-field request should appear in the unresolved report. A separate valid request for `status` should still resolve.
